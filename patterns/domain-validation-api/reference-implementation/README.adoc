[WARNING]
.Not production software
====
This is a reference implementation of the link:../domain-validation-api-pattern.adoc[Domain Validation API pattern →].
It deliberately omits security: there is no authentication, no authorisation, no transport security, no secrets handling and no hardening of the runtime.
Do not use it as-is in production.
====

The payments bounded context with one validation, `name-iban-match`: does the name the payer provides match the name of the holder of the account with the given IBAN?
It is a Spring Boot service that follows Hexagonal Architecture, with the validation as one vertical slice, answered synchronously or asynchronously.

[NOTE]
====
The implementation is being built test-first, one slice at a time: so far the verdict model, the `name-iban-match` domain, its use case with the domain service that implements it, the client of a simulated payee verification scheme, and the controller, answering synchronously or, with the link:../validation-execution/README.adoc[validation-execution starter →], asynchronously.
====

== Build and test

Requirements: Java 25, Node 24 with npm, a GitHub token that can read packages, and Docker for the contract and system tests.
The Gradle wrapper downloads Gradle itself, and the build provisions the Java toolchain when it is missing.

The Domain Validation API rule pack is published on GitHub Packages, which needs a token even for a public package.
Add your GitHub user name and a classic token with the `read:packages` scope, and nothing else, to `~/.gradle/gradle.properties`, never to this repository:

[source,properties]
----
gpr.user=<your GitHub user name>
gpr.key=<the token>
----

In CI, the workflow passes the `GH_READ_PACKAGE_TOKEN` secret instead.

The service implements the `domain-validation-api` contract, at the `apiContractVersion` in `gradle.properties`.
The build publishes it from the specification library in link:../../../api/README.adoc[`api/` →] with the API-Only Publisher, which is why it needs Node, and the API-Only Subscriber fetches it and checks it against `apionly.lock`.
OpenAPI Generator generates the controller's interface and models from it into `build/`.

[source,console]
----
./gradlew build
----

`build` runs every test suite, the coverage gate, the mutation gate and the architecture rules:

[cols="1,3",options="header"]
|===
|Suite |What it covers

|`test`
|Unit tests: one class at a time, everything outside it mocked, no Spring context.
They carry both quality gates: 100% coverage of the project's own code, and a 100% mutation score with PIT, so every behaviour is verified and not just run.

|`testComponent`
|Component tests: one component with everything outside it mocked, no Spring context.

|`testContract`
|Contract tests: the running service against its API contract, generated by the https://github.com/Arc-E-Tect/SoftwareEngineeringDoneRight-API/tree/main/api-only-transcriberj[API-Only TranscriberJ ↗] from the subscribed contract.
Every HTTP case runs through Spring REST Docs; the event runs through Microcks, against Kafka in Docker.
Two success cases are disabled, as the decision log explains: the TranscriberJ cannot yet tell that `Prefer: respond-async` selects `202`.

|`testSystem`
|System tests: the BDD features, one per API operation and one each for the webhook and the event, against the running service.
WireMock plays the webhook's subscribers, and Kafka runs in Docker through Testcontainers.

|`testArchitecture`
|Architecture tests from the https://github.com/Arc-E-Tect/SoftwareEngineeringDoneRight-Gradle[Architecture Validator ↗]: its built-in Hexagonal rules, the Spring rule pack and the Domain Validation API rule pack.
Their reports are in `build/reports/architecture-validator`.
|===

== Run

[source,console]
----
./gradlew bootRun
----

The service listens on port 8080, under `/payments`.
Its payee verification scheme is simulated; `src/main/resources/application.yaml` lists the accounts it knows, which are those of the contract's examples, and which countries it covers:

[source,console]
----
curl -s -X POST http://localhost:8080/payments/v1/validations/name-iban-match \
     -H 'Content-Type: application/json' \
     -d '{"iban": "NL91ABNA0417164300", "accountHolderName": "Jan de Vris"}'
----

[source,json]
----
{"validation":"name-iban-match","outcome":"invalid","details":{"match":"close","registeredName":"Jan de Vries"},"findings":[{"rule":"NAME_IBAN_MISMATCH","severity":"error","message":"The name is close to, but not the same as, the name of the account holder.","pointer":"/accountHolderName"}]}
----

With `Prefer: respond-async` and an `Idempotency-Key`, the validation runs as a job, which the `Location` of the `202` answers:

[source,console]
----
curl -s -i -X POST http://localhost:8080/payments/v1/validations/name-iban-match \
     -H 'Content-Type: application/json' \
     -H 'Prefer: respond-async' \
     -H 'Idempotency-Key: 3f1c9b0e-6a2d-4f7e-9c41-0b8a5e2d7c11' \
     -d '{"iban": "DE89370400440532013000", "accountHolderName": "Anna Schmidt"}'
curl -s http://localhost:8080/payments/v1/validations/name-iban-match/<validationId>
----

Once a job has run, the service tells so with the contract's `ValidationCompletedEventV1`, which refers to the job.
It posts it to the subscribers of the `validationCompleted` webhook, none by default, and sends it to the topic `payments.validation.completed.v1` when Kafka is turned on, which it is not by default, so the service runs without a broker.
With a broker on `localhost:9092` and a subscriber listening on port 9000:

[source,console]
----
./gradlew bootRun --args='--validation.execution.events.kafka.enabled=true --spring.kafka.bootstrap-servers=localhost:9092 --validation.execution.events.webhook.subscribers=http://localhost:9000/hooks/validation-completed'
----

The link:../validation-execution/README.adoc[validation-execution starter →] lists these settings.

== Known limitations

Besides the security it deliberately omits, the example simplifies what a production service would need to decide on.
The link:../../../docs/decision-log.adoc[decision log →] has the reasons.

* Names are compared after folding case, diacritics and Unicode whitespace only.
There is no NFKC normalisation, so full-width letters and ligatures stay as they are, and no transliteration, so `ß` is not `ss` and `Ø` is not `O`.

== Versioning

The version is in `gradle.properties`.
The CI build calculates the next version with semantic-release from the commits that touch this project, and builds with it; no version is released or published.
