The reusable asynchronous execution of validations from the link:../domain-validation-api-pattern.adoc[Domain Validation API pattern →], as a Spring Boot starter.
It chooses between answering a validation at once and running it as a job, makes submitting a job idempotent, keeps track of the job's lifecycle, and finds a job for the job resource, which each validation's controller serves.
It contains no business logic: a bounded context includes it, and supplies its own validations and job store.

The link:../reference-implementation/README.adoc[reference implementation →] uses it for the `name-iban-match` validation.

[WARNING]
====
Like the reference implementation, this starter deliberately omits security and must not be used as-is in production.
====

== Using it

A bounded context depends on the starter; its auto-configuration provides a `ValidationExecution`, which a validation's controller hands its work to:

[source,java]
----
@Override
public ResponseEntity<NameIbanMatchResultV1> validateNameIbanMatch(
        NameIbanMatchRequestV1 request, String prefer, String idempotencyKey) {
    ValidateNameIbanMatchCommand command = mapper.toCommand(request);
    return execution.run("name-iban-match", prefer, idempotencyKey, command,
            () -> switch (useCase.validate(command)) {
                case Checked checked -> mapper.toResult(checked);
                case UnsupportedCountry refused -> throw NameIbanMatchProblems.unsupportedCountry(refused.countryCode());
                case InvalidChecksum refused -> throw NameIbanMatchProblems.invalidChecksum();
            });
}

@Override
public ResponseEntity<NameIbanMatchJobV1> getNameIbanMatchJob(String validationId) {
    return execution.job("name-iban-match", validationId, mapper::toJob);
}
----

`run` answers `200` with the result, unless the request has `Prefer: respond-async`.
Then it submits the validation as a job under the request's `Idempotency-Key`, and answers `202` with the job, its `Location` and `Retry-After`; without a key it answers `400`, and for a key used before with a different request `422`.
The request it is given, the use case's command, is what it compares; a problem the validation answers with, as an `ErrorResponseException`, fails the job with that problem.

`job` answers the job of the validation, mapped as the controller says, with `Retry-After` while it is pending, or `404`.
Every answer has `Cache-Control: no-store`.

Jobs run on virtual threads, and are kept in memory unless the bounded context supplies its own `ValidationJobStore`.

[cols="2,1,3",options="header"]
|===
|Setting |Default |What it is

|`validation.execution.retry-after`
|`1s`
|How long a client waits before it reads a pending job; whole seconds, at least one.

|`validation.execution.problem-types`
|`https://api.example.com/problems/`
|The base of the types of the problems the starter answers with: `invalid-request`, `idempotency-key-reused`, `validation-job-not-found` and `internal-server-error`.
|===

== Build and test

Requirements: Java 25.
The Gradle wrapper downloads Gradle itself, and the build provisions the Java toolchain when it is missing.

[source,console]
----
./gradlew build
----

`build` runs every test suite, the coverage gate and the mutation gate:

[cols="1,3",options="header"]
|===
|Suite |What it covers

|`test`
|Unit tests: one class at a time, everything outside it mocked, no Spring context.
They carry both quality gates: 100% coverage of the project's own code, and a 100% mutation score with PIT, so every behaviour is verified and not just run.

|`testComponent`
|Component tests: one component with everything outside it mocked, no Spring context.
|===

== Run

A starter does not run on its own; the reference implementation includes it.

== Versioning

The version is in `gradle.properties`.
The CI build calculates the next version with semantic-release from the commits that touch this project, and builds with it; no version is released or published.
