== Architecture

[cols="1,4",options="header"]
|===
|Date |Decision

|2026-11-17
|The example validation is `name-iban-match`: slice package `nameibanmatch`, inbound port `ValidateNameIbanMatchUseCase`, controller `NameIbanMatchController`, generated interface `NameIbanMatchApi`, operationId `validateNameIbanMatch`.

|2026-11-17
|Inbound ports carry `UseCase` as a suffix, not a prefix; the pattern document's prefix was an error.
The terms are inbound and outbound, not driving and driven, everywhere: in the documents, and in package names, class names and comments in the source code.

|2026-11-17
|The red-thread code in SoftwareEngineeringDoneRight-Code is the reference for the hexagonal structure.
Packages per slice: `application.domain.model`, `application.domain.service`, `application.port.inbound` (with `command` and `result`), `application.port.outbound`, `adapter.inbound`, `adapter.outbound` and `configuration`; these are also the Architecture Validator's defaults.

|2026-11-17
|An inbound port takes a command (`application.port.inbound.command`) and returns a result (`application.port.inbound.result`); inbound adapters never depend on the domain model.
As in red-thread, a command is a class that checks its input in its constructor, a result is a sealed interface with one record per way the use case can end (for `name-iban-match`: `Checked`, `UnsupportedCountry`, `InvalidChecksum`), and the inbound adapter switches over it.

|2026-11-17
|A use case is implemented by a domain service named after it, with the suffix `Service`: `ValidateNameIbanMatchService` implements `ValidateNameIbanMatchUseCase`.

|2026-11-17
|The verdict model (`Verdict`, `Outcome`, `Finding`, `RuleCode`, `Severity`) is domain model in `...validation.verdict`; each use case returns its own port result, built from the verdict by the domain service.

|2026-11-17
|Beans are wired by an explicit `@Configuration` class per slice, in `...validation.<slice>.configuration`.

|2026-11-17
|Generated OpenAPI code is inbound-adapter code: one generator run per validation tag, into that slice's `adapter.inbound.web.api` package; each slice gets its own copy of the envelope classes.
OpenAPI Generator `documentationProvider=source`.

|2026-11-17
|The asynchronous component (`ValidationExecution`, `SubmitValidationJobUseCase`, `ValidationJobStore`, the job resource) is a Spring Boot starter in its own project, `patterns/domain-validation-api/validation-execution/`, package `com.arc_e_tect.validation.async`.

|2026-11-17
|The pattern rules pack lives in the Library repository next to `hexagonal-spring-rules` and stays as close as possible to how that pack is built and configured; deviations are asked first.

|2026-11-17
|The Architecture Validator's naming conventions are on (`namingConventionsEnabled = true`): inbound ports end in `UseCase`, domain services in `Service`, and controllers in `Controller`.
They stayed off only while the pattern document used a `UseCase` prefix.

|2026-11-17
|A command is a record, so it is immutable and equal by value; it refuses what the domain would refuse by building the domain's `Iban` and `PayeeClaim`, so whichever adapter drives the use case, the use case returns a result and never throws on its input.

|2026-11-17
|A port result owns its own types for the outcome, the match, the severity, the findings and the details, which the domain service maps from the verdict by name; `Checked` has no details when no verdict was reached, as in the contract.

|2026-11-17
|The outbound port `AccountHolderRegistry` (`accountHolderOf(Iban)`, answering a `RegisteredAccountHolder`) comes with the use case in slice 2, because the domain service needs it; its simulated adapter follows in slice 3.

|2026-11-17
|The Architecture Validator counts `configuration` as part of the core, which must not know any adapter, and lets only `configuration` know a domain service's implementation.
So a slice's `@Configuration` wires the core only, the domain service over the outbound port, and the adapters are Spring components that read their own settings: `PayeeVerificationSchemeProperties` in the outbound adapter, `NameIbanMatchProperties` (the supported countries) in `configuration`.

|2026-11-17
|The main class is covered by a unit test that mocks `SpringApplication.run` with Mockito's `mockStatic`, rather than excluded; Mockito runs as a Java agent, as the JDK will refuse a dynamically attached one.

|2026-11-17
|The starter is hexagonal too: the job (`ValidationJob`) is domain model; `SubmitValidationJobUseCase` and `GetValidationJobUseCase` take commands and return port-owned results (`SubmitValidationJobResult`, `ValidationJobView`); `ValidationJobStore` is the outbound port, with an in-memory adapter; `ValidationExecution` is the inbound adapter a validation's controller uses; an auto-configuration wires them.
A bounded context's adapters see the port's types, never the job itself.

|2026-11-17
|The job resource's response is the starter's: `ValidationExecution.job` finds the job through `GetValidationJobUseCase` and answers `404`, or `200` with `Cache-Control` and, while the job is pending, `Retry-After`; the controller passes only its mapping from the job to the contract's job.
This refines the row on the job resource: the controller calls `GetValidationJobUseCase` through `ValidationExecution`.

|2026-11-17
|The reference implementation includes the starter with `includeBuild '../validation-execution'`, as the dependency `com.arc-e-tect.patterns:validation-execution` without a version.

|2026-11-17
|The webhook and the Kafka event are the starter's, so that every validation that uses it tells the same way: `ValidationCompleted` is domain model, `ValidationCompletedPublisher` the outbound port, and `adapter.outbound.event` holds the webhook and the Kafka publisher, which the auto-configuration wires.
`SubmitValidationJobService` publishes to every publisher once the job is stored as it ended, so whoever is told finds the job so; a publisher that fails keeps neither the job nor the other publishers from theirs.

|2026-11-17
|A job keeps its location, the operation's path followed by its identifier, which the `202` answers and the completion refers to; the controller passes `ValidationExecution.run` how to read a result's outcome (`NameIbanMatchMapper.outcomeOf`), as the starter does not know the contract's result.

== API

[cols="1,4",options="header"]
|===
|Date |Decision

|2026-11-17
|OpenAPI 3.1.1 and AsyncAPI 3.1.0.

|2026-11-17
|Publisher target `domain-validation-api`, starting at version 0.0.1.

|2026-11-17
|The server URL ends in `/payments`; paths start at `/v1/validations/name-iban-match`, and the job resource is `/v1/validations/name-iban-match/{validationId}`.

|2026-11-17
|The reference implementation's build runs the Publisher on `api/` and publishes to the `file` channel; the Subscriber reads that directory, locally and in CI. The built `dist/` is not committed.

|2026-11-17
|The reference API's `.redocly.lint.yaml` is reused unchanged; every operation declares `security: []`.

|2026-11-17
|Problem Details follow the reference API: `ProblemDetailsV1` plus one fragment per problem type with `const` type, title and status, served as `application/problem+json`.

|2026-11-17
|The API library lives in `api/` with the reference API's layout: the version in each fragment's file name, fragments grouped by owner (`components/validation/` for the pattern's shared envelope, `common/` for Problem Details, `payments/name-iban-match/` for the validation), and a definition that HTTP and events share kept once in the OpenAPI tree.

|2026-11-17
|The shared envelope is one set of fragments under `components/validation/`, referenced by every target that needs it, not a target of its own: the Publisher builds documents, not stand-alone schema sets.
The pattern document's "published once as a versioned set of schemas" stays as it is; `api/README.adoc` explains how this library realises it.

|2026-11-17
|The `202 Accepted` is one shared response, `ValidationAcceptedV1`, with `Location`, `Retry-After` and `Cache-Control`, and the pending job (`ValidationJobV1`, without a result) as its body.

|2026-11-17
|The job resource is typed per validation: `NameIbanMatchJobV1` extends the shared `ValidationJobV1`, pins `validation` with `const`, and types `result` as `NameIbanMatchResultV1`.
A failed job carries a `problem` with `ProblemDetailsV1`.

|2026-11-17
|The `422` of `name-iban-match` is a `oneOf` of three named problem fragments: `InvalidIbanChecksumProblemV1`, `UnsupportedCountryProblemV1` and `IdempotencyKeyReusedProblemV1`.

|2026-11-17
|A missing `Idempotency-Key` with `Prefer: respond-async` is answered with the shared `InvalidRequestProblemV1`, with an error naming the header.
The header is declared optional, because "required only when asynchronous" needs `if`/`then`, which the TranscriberJ does not type yet.

|2026-11-17
|Problem type URIs: `https://api.example.com/problems/<name>` for the problems every bounded context shares (`invalid-request`, `validation-job-not-found`, `idempotency-key-reused`, `internal-server-error`), and `https://api.example.com/payments/problems/<name>` for those of payments (`unsupported-country`, `invalid-iban-checksum`).

|2026-11-17
|`Idempotency-Key` and `validationId` are lower-case UUIDs, with the pattern from the API repository's guide, so the TranscriberJ can derive valid values, a `400` case and, for `validationId`, a `404` case.

|2026-11-17
|`Prefer` is a plain string, not an enum: RFC 7240 requires a server to ignore preferences it does not support.

|2026-11-17
|`accountHolderName` has `maxLength: 70`, the SEPA limit for a party name, in the contract and in the pattern document's snippet.

|2026-11-17
|`lint.examples` is `error` for both OpenAPI and AsyncAPI: no request, response or message is published without an example.

|2026-11-17
|The API-Only Publisher is a development dependency of `api/`, pinned to 0.19.2; the bundlers are the ones that version pins (Redocly CLI 2.57.0, AsyncAPI CLI 6.2.0).
`build/dist` is the build output and is not committed.

|2026-11-17
|The repository's `pre-push` hook runs the Publisher's `check` when a branch changes `api/`; the Publisher's own `init` hook is not used, as it would compete with the repository's hooks.

|2026-11-17
|`api-build.yml` builds, lints, checks and publishes the library to the `file` channel on every push to a branch that changes `api/`; nothing leaves the runner except the build artifact.

|2026-11-17
|The tag of `name-iban-match` is `Name IBAN Match`, as in the pattern document; it generates `NameIbanMatchApi`, as `NameIbanMatch` does.

|2026-11-17
|The lint warnings of `required-string-property-missing-min-length` on strings fixed by `const`, `enum` or `pattern`, and on `completedAt`, are accepted: a `minLength` there cannot be broken on its own, and would only give the TranscriberJ a case it cannot isolate.
Free-text `detail` members have `minLength: 1`.

|2026-11-17
|`accountHolderName` has the pattern `^\s*\S.*$` (bundle 0.0.2): a name of only whitespace breaks the contract, as the domain refuses it.
It is anchored so that it means the same as a JSON Schema search and as a Java `@Pattern` match.
Java's `\s` is narrower than ECMAScript's, so a name of only, say, em spaces passes the generated validation; the command refuses it, and the controller answers the contract's `400`.

== OpenAPI Generator

[cols="1,4",options="header"]
|===
|Date |Decision

|2026-11-17
|OpenAPI Generator 7.27.0, `spring` generator, with the options of the brief (`interfaceOnly`, `useTags`, `skipDefaultInterface`, `useBeanValidation`, `openApiNullable=false`, `documentationProvider=source`, `annotationLibrary=none`, `requestMappingMode=api_interface`, `unhandledException`), plus `useSpringBoot4` and `useJackson3` for Spring Boot 4.1.2, as in red-thread.
The generated code compiles against Spring Boot 4.1.2; its only compiler warnings are the generator's use of the deprecated `org.springframework.lang.Nullable`, for which it has no option.

|2026-11-17
|Checked on the built contract: `allOf` with `$ref` is flattened into one class that holds the envelope's members; `const` becomes a single-value enum (`ValidationEnum.NAME_IBAN_MATCH`); an optional member is a `@Nullable` field, with no `JsonNullable`; the `oneOf` of the `422` becomes a marker interface that the three problem classes implement.

|2026-11-17
|The generator crashes on a webhook operation without vendor extensions: a `NullPointerException` in `SpringCodegen.reformatProvideArgsParams`, as the operation's extensions map is null.
The service sends the webhook and implements nothing for it, so the generator runs with `--global-property apis=,models=,supportingFiles=`, which leaves webhooks out; the contract is not changed to suit the generator.
`webhooks=false` does not work: a present global property switches its kind on, and its value is a filter of names.

|2026-11-17
|The generated `validateNameIbanMatch` returns `ResponseEntity<NameIbanMatchResultV1>`, typed by the `200` only.
`ValidationExecution.run` is generic and builds the `202` with the job as its body behind one unchecked cast, in that one place, covered by unit and contract tests.

|2026-11-17
|The job resource is implemented per validation: `NameIbanMatchController` implements the generated `getNameIbanMatchJob`, calls `GetValidationJobUseCase` of the validation-execution starter, and maps the job with its own mapper; the starter has no controller of its own.

|2026-11-17
|`generateJsonIncludeAnnotations=true` with `NON_NULL`, so an absent optional member is left out of a response instead of written as `null`, which the contract does not allow.
`generateJsonSetterNullsAnnotations=true` with `optionalNonNullPropertyJsonSetterNulls=FAIL`, so an explicit `null` for an optional request member is rejected with `400`.

|2026-11-17
|The generator runs as the Gradle plugin `org.openapi.generator` 7.27.0 on the subscribed contract, with `FILTER: tag:Name IBAN Match`, and generates the APIs and models only (`apis=,models=`): the supporting files, `ApiUtil` and an `EnumConverterConfiguration` outside the slice, are used by nothing.
`hideGenerationTimestamp=true`, so the same contract gives the same code.
The generated package is left out of coverage and mutation testing.

== Rules pack

[cols="1,4",options="header"]
|===
|Date |Decision

|2026-11-17
|The pattern's rules pack is `domain-validation-rules/` in the Library repository, next to `hexagonal-spring-rules`, published as `com.arc-e-tect.architecture-validator:architecture-validator-domain-validation-rules`, in package `com.arc_e_tect.gradle.architecture.domainvalidation`.
It is built like the Spring pack: Java 21, `-iff` aliases, rule classes in `src/main`, self-tests in `src/test` and fixtures in `src/testFixtures`.

|2026-11-17

The reference implementation adds `..validation.verdict..` to `domainModel`, so the built-in rules guard the shared verdict model.

|2026-11-17
|The pack reads three settings of its own as system properties on the consumer's `testArchitecture` task, as the plugin has no passthrough: `architectureValidator.domainValidation.validationsPackages` (required), `...sharedPackages` (default `verdict`) and `...executionPackages` (default `com.arc_e_tect.validation.async..`).

|2026-11-17

Every rule class name starts with `DomainValidation`, because the plugin warns about two packs contributing test classes with the same simple name.

|2026-11-17
|Each rule has a self-test against a compliant bounded context and one against a violating bounded context of its own; the self-tests follow this repository's conventions, one assertion and a `@DisplayName` each, rather than the Spring pack's several assertions per test.
Like the Spring pack's build, the pack's build has no coverage or mutation gate.

|2026-11-17
|The pack has a build and a release workflow mirrored from the Spring pack's; the release runs on a push to `main` that changes the pack's sources, so merging the pack's pull request publishes it.

|2026-11-17
|The pack is published to the local Maven repository as `1.0.0-PRERELEASE` for Phase 5.
The reference implementation depends on it, so its pull request is not pushed until the pack is published, as the brief requires.

|2026-11-17

Until the pack moves to Maven Central, it is published on GitHub Packages, in the Library repository.

|2026-11-17

== Behaviour of the example

[cols="1,4",options="header"]
|===
|Date |Decision

|2026-11-17
|Names match `exact` when equal after normalising case, whitespace and diacritics, `close` when the Jaro-Winkler similarity is at least 0.90, and `none` otherwise.
Close and no match give finding `NAME_IBAN_MISMATCH` (error, pointer `/accountHolderName`); indeterminate gives `PAYEE_VERIFICATION_UNAVAILABLE` (warning).

|2026-11-17
|One outbound port, `AccountHolderRegistry`, with one simulated adapter, `PayeeVerificationSchemeClient`; no own-bank repository.

|2026-11-17
|The simulation is deterministic: a configured table maps IBAN to registered name; per IBAN an account can be slow (configured delay) or unavailable. A port timeout turns slow or unavailable into `indeterminate`.

|2026-11-17
|A well-formed IBAN that the scheme does not know gives `invalid` with match `none`.

|2026-11-17
|`422` for an IBAN whose mod-97 checksum fails or whose country the scheme does not support; `400` for a request that breaks the schema.

|2026-11-17
|Asynchronous only on `Prefer: respond-async`; then a missing `Idempotency-Key` gives `400`, the same key with the same body returns the existing job, and the same key with a different body gives `422`. In synchronous mode the key is ignored.

|2026-11-17
|Job status `pending`, `completed` or `failed`; `Retry-After` on `202` and on a pending job; a completed job carries the full result; an unknown id gives `404`.

|2026-11-17
|The job store is an in-memory adapter behind `ValidationJobStore`.

|2026-11-17
|Webhook subscriber URLs come from configuration; one best-effort delivery per completion.
The webhook and the Kafka event share one `ValidationCompletedEventV1` schema, which carries a reference only: `validationId`, `validation`, `status`, `outcome`, `completedAt` and the job's location.

|2026-11-17
|Kafka topic `payments.validation.completed.v1`, keyed by `validationId`.

|2026-11-17
|Responses carry `Cache-Control: no-store` and request bodies are never logged; there is no in-service result cache.
|2026-11-17
|A verdict is invalid if, and only if, it has an error finding, and an indeterminate verdict has no details; a finding's pointer is a JSON Pointer that starts with `/`.

|2026-11-17
|The register's answer is domain model, `RegisteredAccountHolder`: registered with a name, unknown, or unavailable; the outbound port returns it.
An unknown IBAN gives the same `NAME_IBAN_MISMATCH` finding as no match.

|2026-11-17
|The domain checks its own input as well as the contract does: an `Iban` has the contract's shape and answers whether its mod-97 checksum is right; a `PayeeClaim` has a name of 1 to 70 characters.

|2026-11-17
|Jaro-Winkler is implemented in the domain, with the standard definition (a matching window of half the longer length minus one, a prefix of at most 4 and a scale of 0.1); the threshold 0.90 is inclusive, shown by `abcd` and `abcdxyzq`, whose similarity is 0.9 exactly.
Names are normalised with `java.text.Normalizer`, so `java.text..` is added to the Architecture Validator's `domainAllowedPackages`.


|2026-11-17
|The countries the payee verification scheme supports are a configured domain value, `SupportedCountries`, given to `ValidateNameIbanMatchService`; the configuration sets the simulated scheme's coverage next to its table of accounts.

|2026-11-17
|The service refuses a failing checksum first and an unsupported country second, both before it asks the register: a mistyped IBAN is the more likely cause, and the payer can correct it.

|2026-11-17
|The outbound adapter is `adapter.outbound.scheme`: `PayeeVerificationSchemeClient` implements `AccountHolderRegistry` over a `PayeeVerificationScheme`, which answers a registered name by IBAN, or none, and fails when it cannot answer.
The client asks the scheme on a virtual thread and waits at most its timeout; when the scheme fails or is too slow it answers `Unavailable` and interrupts the call.

|2026-11-17
|`SimulatedPayeeVerificationScheme` takes an account's response time for real, so that a slow account shows the timeout synchronously and gives the asynchronous execution something to wait for; an unavailable account fails after its response time, and an IBAN that is not in the table has no name at once.

|2026-11-17
|Until the asynchronous execution exists (slice 5), every validation is answered synchronously, as a server may ignore a preference it does not support (RFC 7240), and the job resource answers `404` for every identifier.

|2026-11-17
|Until Problem Details are aligned with the contract (slice 7), the controller answers its problems as Spring `ProblemDetail`s with the contract's type, title and status, through `ErrorResponseException` and `spring.mvc.problemdetails.enabled`; a `400` from the generated validation has Spring's own shape until then.

|2026-11-17
|From slice 5, `Prefer: respond-async` runs the validation as a job, and the job resource answers the job; the synchronous-only behaviour of slice 4 is gone.
`respond-async` is recognised among comma-separated preferences, with or without parameters, in any case (RFC 7240).

|2026-11-17
|With `Prefer: respond-async`, a request the domain refuses is accepted with `202`, and its job fails with the problem the synchronous `422` has; a validation that fails otherwise fails its job with `internal-server-error`.

|2026-11-17
|"The same body" for an `Idempotency-Key` is an equal command: the controller passes the use case's command, which has value equality, so requests that differ only in JSON formatting or member order are the same.
A repeated submission is answered `202` with the job as it is, pending or not.

|2026-11-17
|The `202` has `Location`, the request's path followed by the job's identifier, `Retry-After` and `Cache-Control: no-store`, and the job as its body.
`Retry-After` is `validation.execution.retry-after`, whole seconds and at least one, 1 second by default; the shared problem types are names below `validation.execution.problem-types`, `https://api.example.com/problems/` by default.

|2026-11-17
|Jobs run on virtual threads; the in-memory store keeps every job for as long as the service runs, which suits the example and not a service that runs for long.

|2026-11-17
|From slice 7 the service answers the contract's problems, which supersedes the slice-4 arrangement: `ContractProblemHandler`, in the reference implementation rather than the starter, answers a request that breaks the contract with the invalid-request problem and what fails unexpectedly with the internal-server-error problem, which says nothing of what failed.
It applies to the whole service, as a request without a body is refused before a controller is chosen; such a request has no `Content-Type` either, and is a `400` rather than a `415`.
Every problem, these and those the service answers itself, is `Cache-Control: no-store`.

|2026-11-17
|The invalid-request problem has an error for every place the request breaks the contract that can be named: a member of the body by its JSON Pointer, from bean validation or from Jackson for a wrong type or an undeclared member; a header or a path parameter by the name the contract gives it, so a malformed `validationId` is a `400`.
A body that breaks the contract as a whole, an array or text that is not JSON, has no errors; the service rejects body members the contract does not declare (`spring.jackson.deserialization.fail-on-unknown-properties`).

|2026-11-17
|Publishing to Kafka is off unless `validation.execution.events.kafka.enabled` is `true`, so the service runs without a broker; `spring-kafka` is an optional dependency of the starter, and its topic, `validation.execution.events.kafka.topic`, is the bounded context's, `payments.validation.completed.v1` in the reference implementation.
The key and the event are sent as text, through a template derived from Spring Boot's producer factory, whatever serializers the application configures; a send that fails is logged.

|2026-11-17
|The webhook's subscribers are `validation.execution.events.webhook.subscribers`, none by default; each gets one `POST`, which may take `validation.execution.events.webhook.timeout`, 5 seconds by default; a subscriber that answers with an error or cannot be reached is logged and skipped.
