== Testing conventions

[cols="3,1,4",options="header"]
|===
|Requirement |Status |Evidence

|The test taxonomy: unit, component, contract and system tests; never "integration test"
|Met
|Suites `test`, `testComponent`, `testContract`, `testSystem` and the validator's `testArchitecture`, declared in `testing { suites { } }`; the term appears only in the rule that forbids it.

|One assertion per test
|Met
|Every test method asserts once; the two disabled contract tests delegate to their generated test.

|`@DisplayName` on every test
|Met
|Every test method and every test class carries one; the generated contract tests carry their own.

|Idempotent, independent tests
|Met
|Unit and component tests share no state; the system tests share one service, so every scenario uses an `Idempotency-Key` of its own; the stateful contract tests arrange their own state.

|BDD features per API operation
|Met
|`validate-name-iban-match.feature` and `get-name-iban-match-job.feature`, plus one for the webhook and one for the event, as the next table shows.

|Contract tests through the TranscriberJ
|Met, with one approved exception
|`testContract`: every HTTP case through the REST Docs emitter, and the event through the Microcks emitter; see <<exceptions,Exceptions §>>.

=== What the features cover

[cols="2,3",options="header"]
|===
|The brief asks for |Scenario

|An exact, a close and no match
|_The name is the registered name_; _The name is close to the registered name, which is returned so the payer can correct it_; _The name is somebody else's_; _The scheme does not know the account_.

|An indeterminate verdict
|_The scheme cannot answer, so the payer can decide whether to pay_ (unavailable, and too slow).

|`400` and `422`
|_A request that breaks the contract says where_; _A request that breaks the contract as a whole_; _A request without a body_; _An Idempotency-Key that is not a lower-case UUID_; _An identifier that is not a lower-case UUID is refused_; _The scheme does not cover the account's country_; _The IBAN has the wrong check digits_.

|`202` with polling
|_The payer prefers an asynchronous answer_; _A job that has not run yet says when to read it again_; _A job that has run carries the result_; _There is no validation job with the identifier_.

|The same `Idempotency-Key`
|_The same request with the same Idempotency-Key gets the same job_; _Another request with the same Idempotency-Key is refused_; _An asynchronous answer needs an Idempotency-Key, so that a retry does not start a second job_.

|Webhook delivery
|_A subscriber is told that a job completed, and where to read it_; _A subscriber is told that a job failed, without an outcome_; _A subscriber that answers with an error keeps neither the others nor the job from theirs_.

|Kafka publication
|_The completion of a job is published, keyed by the job's identifier_; _An indeterminate verdict is published as such_; _The failure of a job is published, without an outcome_.
|===

== Exceptions

Each exception was approved by the maintainer and is recorded in the decision log.

[cols="2,3",options="header"]
|===
|Exception |Why

|The generated contract tests `success-202-required` and `success-200-full` are disabled, with their reason.
|`Prefer: respond-async` selects whether the service answers `200` or `202`, and the TranscriberJ cannot tie a response to a header, so it expects each status for both requests.
Their counterparts, `success-200-required` and `success-202-full`, run.
They are enabled again once the TranscriberJ can express a response that a header selects.

|The `422` and `500` responses have no generated contract cases.
|The TranscriberJ derives a case only for a response the contract alone can provoke, and reports these as not covered; the system features cover the `422`s, and the handler's unit tests the `500`.
|===
